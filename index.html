2 · Models

Model strategy: pick by task, not by hype

Expensive

Best quality

Top Opus or GPT-5 class. Planning, architecture, tricky debugging.

Default

Best value

Sonnet, GPT-5 mid tier, Gemini Pro. Most daily coding happens here.

Bulk

Cheap and fast

Haiku, mini, Flash, DeepSeek. Search, tests, boilerplate, subagents.

Mix models: strong model to plan and review, cheap model to execute repetitive steps.

2 · Models

Local models vs cloud models

Local / self-hosted

Run on your own machine

Open-weight models (DeepSeek, Qwen, Kimi, Llama) served via Ollama, vLLM, or a private server.

  • Zero data leaves the machine
  • No per-token billing
  • Slower, less capable than top cloud models
  • Needs hardware and maintenance
Cloud / API

Provider runs the model

Claude, GPT, Gemini, and others via API or managed plans.

  • Best quality and fastest improvement
  • Pay per use; cost scales with usage
  • Code may leave your network
  • Check retention and training terms

Local is for privacy and cost at scale. Cloud is for quality and speed. We use both.

2 · Models

Balanced workflow: when to use each

Local first

Chat sessions, questions, and small edits.

  • Quick questions and brainstorming
  • Explaining existing code
  • Boilerplate and scaffolding
  • Anything with no secrets and no need for top quality

Cloud first

Hard work that needs the strongest model.

  • Planning architecture and large refactors
  • Tricky bugs and security-sensitive logic
  • Reviewing PRs and writing tests
  • Anything where the answer must be right

Rule of thumb: local for speed and privacy, cloud for quality. Escalate when the task gets hard or sensitive.

3 · Concepts

Task, skill, agent, and project memory

Task

One bounded unit of work with a clear definition of done. Small tasks succeed more often.

Skill

Reusable instructions (SKILL.md): how we write migrations, run E2E tests, and so on.

Agent (subagent)

Separate context with its own role, tools, and model. E.g. a read-only reviewer.

AGENTS.md

Project memory: commands, conventions, folder layout, and do-not rules. Read at every session start.

3 · Concepts

Minimal starter setup

  1. Pick one harness and one default model for the team
  2. Add AGENTS.md to each repo: stack, commands, style rules, forbidden paths
  3. Create 2 to 3 skills for your most repeated tasks
  4. Add a read-only reviewer agent for pull requests
  5. Require branch + tests + human review for every AI change

  "allow": [
    "Bash(npm test)", "Bash(npm run lint)",

    "Read(./src/**)", "Edit(./src/**)"
  ],
  "deny": [
    "Read(./.env*)", "Read(./secrets/**)",
    "Bash(curl *)", "Bash(rm -rf *)",
    "Bash(git push *)", "Edit(./infra/prod/**)"
  ]
}

Illustrative. Map to the real format of our chosen harness.

5 · Security

Threats to know

Prompt injection
Instructions hidden in issues, docs, web pages, or dependencies can steer the agent.
Malicious plugins / MCP servers
Vet every tool, skill, and extension like a dependency; pin versions.
Hallucinated packages
Verify every new dependency exists and is maintained.
Silent weakening
Agents may disable tests to pass. Protect test and CI config with code owners.

5 · Security

Secrets and data handling

  • Keep .env files, keys, and tokens out of the agent's readable paths
  • Use short-lived, scoped tokens. Never give production or cloud admin credentials
  • Check provider data retention and training terms; prefer enterprise plans
  • Run a secret scanner (e.g. gitleaks) in pre-commit and CI
  • Restrict network egress from agent sandboxes to allow-listed hosts

5 · Security

Safe-path checklist

  • Agent works in a branch or worktree, never on main
  • Deny rules cover secrets, prod infra, and git push
  • Pre-commit: secret scan, lint, tests
  • CI: required checks and code-owner approval on sensitive paths
  • Session and command logs kept for audit where supported
  • Written team policy: what data may enter prompts, and what must never

6 · Before we start

Before you start (1/2): policy and people

Acceptable use policy
Classify data: public, internal, confidential, personal or regulated. Define what may go into prompts.
Approved tools and models
Vendor review: data residency, GDPR, retention, and contract terms.
Ownership
The developer who opens the PR owns the code. AI is never the author of record.
Licensing and IP
Check dependency licenses and generated code similarity; involve legal where needed.

6 · Before we start

Before you start (2/2): process and measurement

Baseline metrics now
Cycle time, review rounds, escaped defects, and effort per task, so we can prove impact.
Low-risk pilot repo
Good test coverage, clear ownership, no critical production path.
Cost guardrails
Per-user budgets, usage dashboards, and alerts from day one.
Incident process
If a secret or customer data leaks into a prompt: rotate, notify security, record the event.
Opt-in culture
No pressure to adopt. Share what works in a team log; review AGENTS.md in retros.

6 · Before we start

Where to be extra careful

Needs senior review

Authentication, authorization, cryptography, payments, and data-deletion logic.

Avoid unsupervised

Production hotfixes, infrastructure changes, and migrations on real data.

Good early wins

Unit tests, docs, refactors with tests, boilerplate, and code explanations.

Common anti-patterns

Merging code nobody read, "fixing" failing tests by weakening them, skipping review.
